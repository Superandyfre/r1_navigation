# UI7 求解失败恢复、数值稳定性与启动版本一致性改进方案

日期：2026-10-30  
目标分支：`codex/navigation-environment-snapshots`  
状态：实施规划。本文中的新增恢复机制尚未实现，不代表实机验收通过。

## 2. 重新划分故障，允许新目标重新尝试

当前调用链将求解异常归为通用 `worker_response_failure`，丢失了恢复决策所需的分类信息。应保留底层原始错误、请求上下文和求解状态，避免把可识别的数值不收敛直接等同于进程崩溃。

| 类型 | 处理方式 | 新目标的恢复条件 |
| --- | --- | --- |
| ECOS 达到迭代上限，未得到可接受解 | 本次结果无效，输出零速度，报告可恢复失败 | 新任务清除旧求解状态，用最新输入重新计算 |
| 路径受阻、绕障候选全部无效 | 有界等待、重规划或结束当前任务 | 允许新目标重新计算；仍需通过几何检查 |
| Worker 崩溃、IPC 损坏、协议身份冲突 | 致命故障停车 | 新目标不能直接清除故障，执行受控恢复 |
| NaN、Inf、结果结构错误 | 按致命故障处理 | 不能通过换目标绕过校验 |
| 定位未就绪或失效 | 阻止运动并显示定位原因 | 先按现有定位流程恢复，再检查其他运动条件 |

只有能够可靠识别、完整传递的求解不收敛才能进入可恢复分支。不能通过捕获所有异常并标记“可重试”来掩盖代码错误、数据损坏或进程失效。

恢复的前提是生成新的有效结果；收到新目标本身不构成运动许可。新目标处理顺序为：

1. 撤销旧任务运动授权，保持零速度。
2. 建立新的任务身份，清除旧轨迹、绕障引导、失败计数和求解初值。
3. 使用最新定位、里程计、障碍数据和新路径重新求解。
4. 新结果通过数值、几何、时效、版本及现有授权检查后，才恢复运动。

旧目标迟到的结果不能进入新任务。新目标只能重置可恢复的任务失败状态，不能清除已锁存的致命故障。明确的新任务身份不得仅由终点坐标推断；取消、抢占和重复相同目标的语义需与现有执行归属协议一致。

建议在既有响应信封内增加明确的规划结果分类，例如 `success`、`recoverable_solver_failure`、`blocked`，同时保留原始求解器状态与错误摘要。字段命名与 schema 版本在实施中确定；若改变协议，应同步更新生产者、消费者、混版拒绝检查和发布清单，不能静默改变旧字段含义。

### 2.1 按恢复层级区分“卡住”

| 层级 | 判定证据 | 恢复动作 | 退出条件 |
| --- | --- | --- | --- |
| R1：单次求解不收敛 | 当前请求收到完整、身份匹配的数值失败响应，进程及通信仍健康 | 零输出、清除不适用的求解缓存、使用最新输入有限重试 | 新有效结果通过检查，或升级为当前任务失败 |
| R2：持续规划失败/路径受阻 | 连续求解失败，或有效候选始终不能通过通行检查 | 有界重规划、重建绕障引导；终止失败任务后可接收新目标 | 新路径可执行，或预算耗尽并报告失败 |
| R3：有有效解但实际不前进 | 非零运动请求与新鲜有效结果存在，但里程计和路径进展持续不足 | 区分执行链阻断、几何受困与底盘未响应，再选择对应处理 | 恢复实际进展，或明确报告受困/执行异常 |
| R4：进程或运行协议失效 | Worker 崩溃、IPC/协议异常、无效数值等致命证据 | 撤权、故障停车；按第 3.2 节受控恢复 | 建立全新有效运行上下文，等待新目标 |

若 Controller/Guard 正在拒绝非零请求，应先报告具体拒绝原因；不能将授权阻断当成障碍受困并追加运动。若最终非零速度已输出但底盘没有响应，应报告执行或硬件异常，不能连续加大速度或反复倒车“试出来”。输入陈旧或定位不可靠时，不进入自主脱困。

## 3. 实现有界重试，避免永久停用或无限重算

同一目标不应因一次数值失败永久停用，也不能无限重算。建议采用以下初始策略，具体预算依据现场耗时校核后固定：

1. 首次求解失败：立即输出零速度，保存原始错误与诊断。
2. 获取最新输入，清除不适用的热启动缓存，允许一次重新求解。
3. 再次失败：结束当前 FollowPath，明确返回规划求解失败，允许现有 BT 执行一次重新规划。
4. 重规划后仍未恢复：结束当前导航任务，保持停车，等待新目标。

重试次数以导航任务为单位累计，不能因每秒路径更新而归零。计数必须覆盖该任务下的 FollowPath 重建与 BT 重规划，不能只放在会随 action 重建而重置的局部对象中。

恢复成功应经过明确的稳定运行窗口后再清除连续失败记录，避免成功与失败交替时长期顿挫。稳定窗口和单次/累计重试预算均需记录在配置和诊断中。

连续失败计数与任务累计预算分开：稳定恢复只能清除连续失败计数，不能刷新该任务的累计重试、脱困次数和累计恢复耗时上限。每个恢复动作均使用单调时钟截止时间；计数、单次耗时和累计耗时任一耗尽即退出。单次有效解或一次短暂转动不能无限延续恢复。

上述重试不重启 Worker，不清除真正的致命故障，不延长现有运动来源有效期。清除缓存或发起重试之前先保证无效结果不能继续授权运动；失败期间不得复用旧非零指令续命。

### 3.1 跨组件恢复契约

仅改变 Worker 的异常分类不构成恢复完成。必须逐层验证以下契约：

| 组件 | 可恢复失败时 | 新目标/恢复成功时 |
| --- | --- | --- |
| Worker 与 IPC | 返回明确失败类别和原始求解信息；不得携带可执行速度，不伪装成功；仍能接收请求 | 新目标清除旧求解状态，关联新的任务与请求；继续使用最新输入 |
| ROS2 主节点 | 发布零命令及对应失败状态；禁止把结构完整的失败响应当成有效规划结果 | 新的有效结果通过后处理与版本检查后才成为运动来源 |
| Controller | 区分当前规划失败与致命故障；原有结果超时机制继续约束输出 | 同任务重试按协议恢复；新任务使用新身份；没有残留的错误致命锁存 |
| Guard | 没有当前有效结果时零输出；不以健康心跳代替规划结果 | 仅在当前来源及授权握手全部满足后放行，不接收旧来源重放 |
| BT/任务管理 | 执行有限重规划，保存任务累计预算，正确结束失败或取消的任务 | 新任务不继承旧轨迹和等待状态；不重启已取消任务 |

若可恢复等待超过现有截止时间并触发运行故障，不能直接清除故障继续运行；应先修正恢复协议及其时序，或转入受控恢复。不得简单延长健康/授权超时使测试通过。

任务预算与取消状态应由能够覆盖同任务下多次 FollowPath 的现有导航接入管理层维护。UI7 使用 Nav2 BT 现有运行边界；CogNav 生产代码不在本次修改范围内。不能宣称 CogNav 已适配新增自动重试；直接 FollowPath 客户端至少仍具备失败终态、新目标独立重试及既有身份隔离语义。

### 3.2 致命故障后的受控恢复入口

增加或明确一个受控运行恢复入口，使真正的进程故障可以在不重启整台机器的情况下救回。它与“新目标重试”分开，也不等于增加正常导航的手动 arm 步骤；正常启动仍按既有就绪条件自动启用。

恢复流程：

1. 停止接收旧任务的运动执行，撤销旧授权；通过独立输出与新鲜里程计确认零输出及底盘静止，不能只看 action 已结束。
2. 保存首次故障及最小诊断，停止失效组件，确认旧进程/Worker 已退出。停止或确认失败则恢复失败，保持停车。
3. 按故障范围重建所需组件，生成新的 boot/generation/执行上下文。必要时重建完整 UI7 导航组件集合，不能只清空一个 Python 布尔值。
4. 重新检查版本来源、通信、扫描、里程计、定位、轮廓及 Guard 状态；旧命令、旧授权和迟到消息不能跨恢复边界生效。
5. 全部就绪后进入“等待新目标”；不恢复旧目标、不继承原任务重试动作、不自动继续故障前的非零指令。

每次入口调用只有一个恢复操作，设置明确期限；重复调用合并或拒绝，不形成重启循环。失败时报告失败阶段和原始故障并保持停车，允许现场排查后再次明确发起恢复。不得启动或停止无关 CogNav、UI8、底盘、机械臂驱动进程。

该入口需通过进程崩溃、停止超时、重建失败、重复请求、旧消息重放和恢复中取消的隔离验证后才用于现场。恢复成功的证明包括旧进程退出、新身份就绪、无目标零输出和新目标可执行，不能仅以服务返回 success 判定。

## 4. 修复 ECOS 不收敛的数值原因

离线重放是本阶段的主入口。先对相同现场输入建立可重复基线，再区分数据问题、状态问题和问题条件数问题。

### 4.1 检查项

- 输入、目标函数、约束矩阵和常量是否有限，数值尺度是否相差过大。
- 障碍距离线性化是否退化，是否存在重复或近乎重合的约束。
- 速度、加速度、当前测量速度和路径参考是否产生冲突。
- 路径、档位或绕障阶段切换后是否沿用不适用的热启动状态。
- 强惩罚项与距离变量是否造成病态问题。
- 失败发生在哪个求解子阶段，以及原始返回码、残差、对偶间隙和耗时。

### 4.2 修复顺序

1. 优先修复输入构造和状态重置错误。
2. 对确认存在的问题实施变量或约束尺度归一化，保持物理含义及约束不变。
3. 在同一现场输入上比较求解状态、约束残差、轨迹和耗时。
4. 只有确有必要才评估备用求解器；备用求解器的“成功”不能替代独立结果校验，也不能直接触发速度发布。

不接受负返回码的结果；近似解必须沿用明确、可验证的接受标准。不得通过放松碰撞约束强行获得解，不使用失败结果中的速度作为降级输出，不把增加迭代次数或放大超时作为默认修复。

验收时须区分“本输入得到有效解”和“本输入被正确识别为可恢复失败”。后一种可以证明故障处理正确，不能证明数值收敛问题已经解决。

### 4.3 数值修复的独立验收标准

建立有校验值和来源清单的小型回归集合，至少包含当前稳定复现的失败锥规划、对应完整求解上下文（能够采集时）、相邻正常样本及相关阶段切换样本。缺失完整上下文时明确记录，不能把单次锥规划重放替代完整有状态求解验证。大数组单独保存，Git 记录采集版本、求解器/依赖版本、路径及 SHA256。

将以下验证分别执行和记录：

1. 固定锥规划重放：相同输入多次重放，记录返回码、原始尺度下的约束残差、间隙、解的有限性、迭代数与耗时。若采用尺度变换，须还原到原物理尺度检查，不能只看缩放后的残差。
2. 完整求解链重放：检查参考路径、热启动、机器人几何、障碍映射及阶段切换；证明修复后的输入生成过程没有改变约束含义或再次产生同类退化问题。
3. 正常样本对照：比较轨迹、控制、净空、求解成功率与 p50/p95/最大周期耗时；确认没有以明显降低导航质量或违反现有运行预算换取成功。

残差、几何、近似解接受标准和性能预算在评估前固定并记录。只有已复现失败样本获得经独立检查的有效解，且正常对照无不可接受退化，才能标记“本次数值修复通过”。若只能可靠识别失败并停车，则只标记“容错恢复通过”，数值问题继续保持未完成。

备用求解器如确需引入，也必须受同一总求解期限、任务预算和结果检查约束。备用路径耗尽预算后返回明确失败，不得串联无上限尝试，也不能为运动来源重新打时间戳掩盖输入过期。

## 5. 与既有路径、绕障修复衔接

保留 `unified-03` 已加入的路径连续更新、绕障接回、候选拒绝诊断和有限引导重建，并落实以下约束：

- 常规重规划保持当前执行身份及任务级失败预算。
- 新任务清除旧绕障状态、轨迹与求解缓存。
- 绕障候选无效属于规划失败，不直接等同于 Worker 进程故障。
- 绕障退出必须满足接回路径的几何、方向、路径匹配及稳定条件。
- 求解失败期间不继续发送先前的非零指令。
- 身份、路径版本、Worker 代际、输入和结果新鲜度检查继续有效。

隔离测试通过不代表真实路径质量、通行能力和持续运行稳定性已经通过验收。现有正常速度与避障参数先保持，待逻辑和时序稳定后再分别评估，避免同时改动导致无法归因。

### 5.1 有限自主脱困

自主脱困作为单独能力实现和验收，不能把“换目标可以重试”称为“已经能够自主脱困”。允许其处理可感知、存在安全运动空间的几何受困场景，不保证在无通路、障碍贴身或感知不足时自行脱离。

停滞检测同时使用实际里程计、当前位置在路径上的有效进展、目标距离变化、最终输出及 Controller/Guard 放行状态。区分正常等待、到达减速、合法原地转向与真实停滞；在定位重定位、输入陈旧或停车请求期间不得触发运动恢复。脱困成功以实际有效进展判定，不能仅用求解器预测进展或发出非零命令判定。

恢复动作按以下顺序执行：

1. 停车，使用最新障碍数据重新规划。
2. 有限重建绕障引导，评估另一侧可行性，避免左右反复切换及重复相同失败动作。
3. 存在经过检查的安全空间时，选择有限原地转向或短距离后退，随后重新规划并接回路径。
4. 无安全候选、实际未取得进展或预算耗尽时，结束任务并报告受困，允许现场处理后重新提交目标。

每个动作必须具备最大距离、角度、速度、持续时间和中止条件，并共同消耗任务累计恢复预算；具体值依据有效感知范围和真实制动能力确定，未确定前不能启用。每个动作后重新评估障碍与实际进展，不连续播放预录制动作序列。

转向或后退必须满足：扫描与 TF 新鲜、定位可信、相应方向具有有效感知覆盖、机器人完整轮廓及机械臂投影可用、动作全过程扫掠检查通过，并继续接受现有独立授权、输入时效和停车约束。后方感知或完整轮廓检查未验证时，后退脱困保持禁用；只修复有界重规划和新目标重试也应可独立交付。

执行期间持续检查上述条件；新障碍、输入失效、轮廓变化、取消或新目标均中止当前脱困，撤销对应命令。新目标按照新任务处理，不能与旧脱困命令交错执行。最终非零输出存在但底盘不响应的场景转为执行异常，不尝试增加动作强度。

## 6. 修复 UI7 启动版本不一致

当前 starterbutton 在创建按钮时保存脚本路径，修改磁盘配置不会更新已创建的按钮。本次已经通过重新加载启动器完成临时纠正；后续采用稳定入口消除这一依赖：

```text
UI7 固定入口
    → 每次点击时读取当前发布版本指针
    → 校验发布清单和关键文件
    → 显式加载固定环境
    → 核对组件来源
    → 启动导航
```

切换时原子更新版本指针，保留上一版本用于回退。既有发布包保持不可变；不能通过覆盖旧 bundle 内容或修改旧路径指向来伪装版本切换。稳定入口本身首次注册后，应重新加载当前打开的启动器。

启动终端必须明确显示发布包编号、构建提交、Controller/Worker/NeuPAN 实际加载路径、地图及配置来源、启动检查结果。组件混用或校验失败时应明确报错停止，不能静默回落到其他环境。

验收必须覆盖：启动器保持打开，更新发布指针后再次点击，实际进程及共享库仍正确加载目标版本。只读取配置文件不足以证明切换成功。

## 7. 分离定位等待与规划失败

运行状态至少区分以下情形，并分别携带原因及对应任务身份：

- 等待定位。
- 等待路径。
- 正在求解。
- 求解失败，准备有界重试。
- 当前任务失败，可以接收新目标。
- 致命故障，需要受控恢复。

重启时允许保存有效定位用于初始化，但前提是机器人静止、里程计连续、地图一致且数据足够新。必须核对位置、朝向、坐标系和数据时效；任一条件不满足时由现场重新定位。

恢复初值后仍须通过正常匹配检查，不能直接设置 READY，不能降低定位收敛阈值。当前未收敛的定位与此前 READY 状态下发生的 ECOS 失败是两个独立问题。

## 8. 实施顺序与最小验证

| 阶段 | 工作 | 完成判据 |
| --- | --- | --- |
| P1 | 求解错误分类及跨进程传播 | 可识别的单次不收敛不永久锁存；真正致命故障仍停车 |
| P2 | 新目标状态重置、有界重试及跨组件恢复 | 新目标重新计算；各层无残留错误锁存；旧结果无法复用；任务预算不被路径更新刷新 |
| P2b | 致命故障受控恢复入口 | 旧执行彻底撤销；有界重建并获得新身份；等待新目标；失败仍停车 |
| P3 | 现场 ECOS 数值问题修复 | 满足第 4.3 节标准；仅实现正确失败处理不能标记本阶段完成 |
| P4 | 停滞检测与有限自主脱困 | 区分规划/执行/几何受困；安全候选才运动；实际无进展有界退出；后退按条件启用 |
| P5 | UI7 固定入口与版本校验 | 启动器保持打开时切换版本，再点击加载正确发布包 |
| P6 | 独立构建与隔离验证 | 目标切换、失败恢复、脱困取消、致命故障救回及实际加载来源检查通过 |
| P7 | 实机短程验收 | 分别验证数值、任务恢复、有限脱困和受控救回，记录通过范围与未完成项 |

P3、P4 的研究和实现可以在明确接口后分别开展；发布必须按实际完成能力标记。后退条件未满足时保持禁用，不阻塞单次失败恢复的独立发布，也不能因此将完整自主脱困标记为完成。

必要的回归场景限定为：

| 场景 | 预期 |
| --- | --- |
| 单次求解失败后恢复 | 失败期间零输出；新有效结果通过检查后恢复 |
| 持续求解失败 | 重试有明确上限，最终任务退出，底盘保持停车 |
| 失败后发送新目标 | 清除旧任务求解状态，使用最新输入重新计算 |
| 新目标到来时旧结果迟到 | 旧身份或旧版本结果不能发布为新任务命令 |
| 路径持续更新 | 保持执行连续性，也不能无限重置失败预算 |
| Worker 崩溃、IPC/协议异常 | 新目标不能解除致命故障 |
| 无效数值、错误结果形状 | 不降级为普通可重试失败，不产生非零输出 |
| 取消与重试竞争 | 取消优先撤权；迟到重试不能重新启动已取消任务 |
| 启动器缓存与发布切换 | 实际进程和模块来源符合发布清单，混版拒绝启动 |
| 可恢复失败后的跨层状态 | Worker 能接收请求，Controller/Guard 无误锁存，BT 可重试或正常终止 |
| 成功/失败交替及 action 重建 | 连续计数与累计预算分离，不能无限重试或长期顿挫 |
| 有有效解但没有实际运动 | 区分执行链拒绝、底盘未响应和几何受困，不盲目加速脱困 |
| 合法转向、终点减速、定位等待 | 不误判为需要运动脱困的停滞 |
| 有安全空间的转向/后退 | 检查完整轮廓扫掠、方向感知、真实进展和动作预算；无条件不启用 |
| 无通路、后方感知缺失、新障碍 | 不执行不安全动作，预算耗尽后明确受困并允许人工处理后重试 |
| 新目标/取消与脱困竞争 | 旧动作停止，旧结果不能进入新任务，取消不触发补偿运动 |
| 致命故障的受控救回 | 旧进程退出，新身份就绪，无目标零输出，新目标可执行；失败保持停车 |
| 恢复入口停止超时、重建失败或重复调用 | 恢复有期限，无重启循环，不虚报成功 |

先完成离线重放和必要单元验证，再运行带真实 Worker/Controller/Guard 的隔离 ROS 链路。使用独立 ROS 域，不启动真实底盘或双臂驱动；不能仅凭话题重映射宣称隔离。

构建、封装、来源核验通过后，在现场确认停航、静止并保持急停的条件下切换。维护程序不主动发送运动目标；实机按空旷短路径、单障碍绕行、失败后新目标、取消和受阻停车的顺序验收。自主脱困只在对应方向感知、轮廓及动作预算已通过隔离验证后，在可控空旷场地验收；致命故障主动注入先在无硬件隔离链路完成，不直接带运动目标在真机上试错。

记录最终零速度占比、指令最大间隔、规划耗时分布、求解失败/重试次数、任务终态、执行及路径身份。既有 ROS Action 响应偶发超时仍需单独记录，不通过扩大全部超时掩盖。

## 9. 交付、提交与回退要求

- 以阶段划分小提交，更新协议说明、失败分类、默认预算与验收记录。
- 不混入现有未提交的求解器实验、现场日志或其他工作树产物；必要实现从明确的提交基线开展。
- 新运行代码独立构建为新发布包，核对实际加载路径，不在运行进程中热替换代码。
- 版本清单分别记录“源码已保存”“构建通过”“隔离验证通过”“实机验收通过”，不能互相替代。
- 能力清单分别记录“数值修复通过”“单次失败/新目标恢复通过”“有限自主脱困通过”“致命故障受控救回通过”，写明测试集合、预算、禁用动作与适用条件，任何一项通过不能替代其他项。
- 回退前停止当前任务并确认静止，切回完整旧发布版本；不能恢复旧目标或通过回退自动解除运动限制。
- CogNav 生产代码、UI8 及其旧环境保持独立；接口变更以技术说明提供给维护人员，不代其修改生产适配。

交付标准不仅是“重新发目标后又动了”，还必须满足：失败原因可解释、重试有边界、新目标确实重新计算、旧结果不能串入、真正故障仍可靠停车。具备安全空间时能够尝试有限脱困；无安全解时有界退出，现场处理后能重新接收目标；进程故障可经受控重建救回，不需要重启整台机器，也不自动续跑旧目标。数值稳定性、脱困范围及实机效果未验证时应明确保留未完成项。
